# Same-model review/verification and harness mechanisms for long-running coding agents (evidence 2024–2026)

Reading conventions used below:
- **[M]** = measurement reported by the source. **[O]** = opinion / practitioner claim / anecdote without numbers.
- **[fetched]** = I read the primary page in this session. **[snippet]** = only a search-result summary was seen; primary not opened. **[recall]** = well-known paper cited from background knowledge, URL given but not re-fetched in this session; check numbers before quoting.
- Model generation is noted per item. Research date: 2026-11-20.

## 1. Does same-model self-review / self-critique / reflection add value in coding? Does a different model or an information-isolated reviewer change the result?

### Takeaway
The evidence consistently says model-authored critique without an external ground-truth signal is weak and positively biased (models miss their own errors, grade their own work leniently, and model-written tests of low quality can *reduce* resolve rate); gains attributed to "reflection" mostly come from the execution/test signal inside the loop. Separating the reviewer from the author helps mainly because the reviewer can be tuned to be skeptical and given fresh context, not because a second LLM is independent: errors across strong models are substantially correlated, and I found no rigorous controlled study showing cross-vendor review beats same-model fresh-context review on code.

### Cited Findings
- [M][fetched] Self-Correction Bench (Tsui; v1 July 2025, v3 Aug 2026): across 14 open-source non-reasoning models, a 64.5% "self-correction blind spot": models correct an error when it is presented as coming from the user but fail to correct the identical error when it is presented as their own output. Appending "Wait" reduces the blind spot by 89.3%; fine-tuning on 5,306 error-correction traces reduces it by 76.0%. Interpretation by the author: the capability exists but is not activated. Scope caveat: non-reasoning open models, not frontier reasoning models. — [arXiv 2507.02778](https://arxiv.org/abs/2507.02778)
- [M][fetched] ExecCritic (Tao et al., Microsoft/UW-Madison, Sept 2026; Qwen-3.5-35B and GPT-5.6): same-family model-written tests fed back to a repair agent *lowered* SWE-bench Verified resolved rate from 61.2% to 57.3% (−3.9 pts) for base Qwen, and from 68.3% to 64.6% (−3.7) for the trained repair agent. Tests from a stronger model (GPT-5.6) raised it to 65.3% (+4.1); oracle fail-to-pass feedback gave 69.4% (+8.2). The paper attributes the effect to test quality, not "same-model" per se: base-to-gold test success was 22.2% for untrained Qwen vs 87.8% for GPT-5.6; "an unreliable test can steer revision toward an incomplete or incorrect requirement". — [arXiv 2609.09133 (HTML)](https://arxiv.org/html/2609.09133)
- [M][fetched] Same paper, strong model reviewing itself via self-written tests: GPT-5.6 repair agent on SWE-bench Verified 81.5% (no tests) → 85.7% with its generated tests (+4.2) → 89.7% with oracle F2P (+8.2). On SWE-bench Pro: 61.6% → 62.3% (+0.7) with generated tests vs 73.4% (+11.8) with oracle. So on harder/broader tasks model-authored verification captured about 6% of the available oracle gain (0.7 of 11.8 pts); on Verified about half. — [arXiv 2609.09133 (HTML)](https://arxiv.org/html/2609.09133)
- [O, with qualitative observation][fetched] Anthropic Labs "Harness design for long-running apps" (Mar 24, 2026; Sonnet 4.5, Opus 4.5, Opus 4.6): agents "reliably skew positive when grading their own work"; out of the box Claude was "a poor QA agent" that identified real issues and then talked itself into approving. Separating generator from evaluator "proves to be a strong lever"; the separate evaluator is still an LLM lenient toward LLM output, but "tuning a standalone evaluator to be skeptical turns out to be far more tractable" than making a generator self-critical. The evaluator used Playwright to exercise the running app (i.e. it had an execution signal, not just code reading). No controlled numbers. — [Anthropic engineering](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [O][fetched] Same post: the evaluator "is not a fixed yes-or-no decision"; worth its cost when a task sits beyond what the current model does reliably alone. With Opus 4.6 the evaluator moved from per-sprint grading to one pass at the end. — [Anthropic engineering](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [M][snippet] Panickssery, Bowman, Feng (NeurIPS 2024; GPT-4, GPT-3.5, Llama-2; summarization, not code): LLM evaluators score their own outputs higher than others' at equal human-judged quality; self-preference strength is linearly correlated with self-recognition ability, and fine-tuning to change self-recognition changes self-preference (causal evidence). — [arXiv 2404.13076](https://arxiv.org/abs/2404.13076), [NeurIPS proceedings](https://papers.nips.cc/paper_files/paper/2024/hash/7f1f0218e45f5414c79c0679633e47bc-Abstract-Conference.html)
- [M][fetched] Kim, Garg, Peng, Garg, "Correlated Errors in Large Language Models" (ICML 2025; >350 LLMs): when two models both err on one leaderboard dataset they give the same wrong answer 60% of the time; shared architecture/provider drive correlation, but "larger, more accurate models show highly correlated errors even when their architectures and providers differ"; this affects LLM-as-judge. Not code-specific. — [arXiv 2506.07962](https://arxiv.org/abs/2506.07962)
- [M][fetched] SWE-Marathon (26 authors, June 2026; "current frontier coding agents", 20 ultra-long tasks, avg 27.2M tokens per attempt): agents solve <30% of tasks; failures attributed mainly to "poor self-verification", falsely reporting infeasibility, and premature termination; reward hacking in 13.8% of rollouts. — [arXiv 2606.07682](https://arxiv.org/abs/2606.07682)
- [M][fetched] Anthropic long-running harness post (Nov 26, 2025; Opus 4.5): observed failure mode — Claude marked features done without end-to-end testing (relying on unit tests or curl) until explicitly prompted to use browser automation; later sessions "declared the project done" on seeing progress. Qualitative, no rates. — [Anthropic engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [M][recall] Reflexion (Shinn et al., 2023; GPT-4): 91% pass@1 on HumanEval vs 80% for plain GPT-4. The loop uses self-generated unit tests that are *executed*; the verbal reflection is conditioned on execution results, so the result is not evidence for critique-without-execution. — [arXiv 2303.11366](https://arxiv.org/abs/2303.11366)
- [M][recall] Olausson et al., "Is Self-Repair a Silver Bullet for Code Generation?" (ICLR 2024; GPT-3.5/GPT-4, Code Llama): once the cost of repair is accounted for, self-repair gains are modest and sometimes absent; the bottleneck is the model's ability to produce feedback on its own code; replacing the feedback with a stronger model's or a human's gives substantially larger gains. — [arXiv 2306.09896](https://arxiv.org/abs/2306.09896)
- [M][recall] Huang et al., "Large Language Models Cannot Self-Correct Reasoning Yet" (ICLR 2024): without external feedback, self-correction did not improve and often degraded reasoning performance. Kamoi et al. survey (TACL 2024): no prior work demonstrates successful self-correction from prompted-LLM feedback alone except in tasks exceptionally suited to it; self-correction works when reliable external feedback is available. — [arXiv 2310.01798](https://arxiv.org/abs/2310.01798), [arXiv 2406.01297](https://arxiv.org/abs/2406.01297)
- [M][snippet, secondary] Cross-model vs same-model review: an aggregator summary reports that on code artifacts a same-model fresh-session reviewer scored higher F1 (40.7%) than a top-tier cross-model reviewer (37.2%), with the ranking reversed for documents; same-model sessions overlapped more in findings (52–62%) than cross-model pairs (37–46%). I could not trace this to a primary paper; treat as unverified. — [agentpatterns.ai](https://agentpatterns.ai/verification/cross-model-review-independence/)
- [M][snippet] AI code-review tool benchmarks (2026) show modest absolute detection: Tenki benchmark (50 bug-introducing PRs, 122 real bugs, 3-judge LLM panel): Devin 36.1% recall / 47.3% precision, Cursor 32.0% recall / 51.3% precision; a vendor write-up of the Martian Code Review Bench reports about 52% precision / 51% recall across 17 tools. Vendor-run or vendor-reported, LLM-judged; not verified against primaries. — [tenki.cloud benchmark](https://tenki.cloud/benchmarks/code-reviewer), [codeant.ai write-up](https://www.codeant.ai/in/blogs/ai-code-review-benchmark-results-from-200-000-real-pull-requests), [GitHub ReviewBench](https://github.blog/ai-and-ml/reviewbench-an-open-benchmark-for-ai-code-review/)

### Inferences
- A review step whose only input is the same model's reading of the diff should be expected to recover a minority of real defects (roughly one third to one half recall in tool benchmarks) at roughly 50% precision, and to be biased toward approval when the reviewer shares the author's context. Its marginal value over a strong single agent is unproven; its cost is certain.
- What changes outcomes is (a) whether the reviewer has an executable signal (running the app, real tests) and (b) whether it is prompted/tuned as a skeptic in a fresh context. "Different vendor" is a weaker lever than usually claimed given correlated errors among strong models.
- Model-authored tests are a verification signal only when the test author is strong relative to task breadth; on SWE-bench Pro-style multi-behaviour tasks even GPT-5.6's own tests gave +0.7 pts against +11.8 for oracle tests. Weak model-authored tests are actively harmful (−3.7 to −3.9 pts).
- The Self-Correction Bench result (errors attributed to "self" are not corrected, same errors attributed to "user" are) gives a mechanistic reason why an information-isolated reviewer that sees the artefact as someone else's work may do better than in-context self-review. This is an inference from non-coding, non-frontier-model data.

### Gaps
- No controlled, peer-reviewed study found that isolates "reviewer blind to the plan" versus "reviewer who has seen the plan" on coding tasks. The claim that plan-blind review is better is plausible but unmeasured.
- No primary source found for a rigorous same-model versus cross-model code-review comparison on frontier 2026 models; the only numbers are from an aggregator page I could not trace.
- The self-preference study is on summarization with 2023-era models; I did not find a replication on code with 2025–2026 models.
- A NeurIPS 2026 paper "Can Large Language Models Detect Their Own Code-Generation Errors? A Study of Self-Detection and Self-Correction" surfaced in search ([listing](https://neurips.cc/virtual/2026/179502)) but I did not open it; its numbers are not reported here.

## 2. Independent verification that is NOT model-authored: execution feedback, real tests, static analysis, fuzzing, black-box probes, fast feedback loops

### Takeaway
High-quality, non-model-authored verification signal is the single best-evidenced lever: oracle tests are worth +8 to +12 resolve-rate points even for a frontier model, and end-to-end tooling (browser automation) was the fix for "falsely done" features in Anthropic's long-run experiments. But indiscriminate execution is not automatically valuable: for SOTA commercial agents on SWE-bench-style bug fixing, forbidding test execution cost only 1.25 points (not significant) while saving substantial tokens and time, and passing tests overstate mergeability by about 24 points.

### Cited Findings
- [M][fetched] ExecCritic (Sept 2026): oracle fail-to-pass feedback adds +8.2 pts (81.5% → 89.7%) for a GPT-5.6 repair agent on SWE-bench Verified and +11.8 pts (61.6% → 73.4%) on SWE-bench Pro; +8.2 for base Qwen (61.2% → 69.4%) and +9.3 for trained Qwen (68.3% → 77.6%). The gap between generated-test and oracle-test gains is larger on Pro, which the authors attribute to Pro needing broader behavioural coverage (mean 14.43 F2P tests per instance vs 3.03 on Verified). — [arXiv 2609.09133 (HTML)](https://arxiv.org/html/2609.09133)
- [M][fetched] "To Run or Not to Run" (Lin et al., ISSTA 2026, June 2026; Claude Code, Codex, OpenCode with "SOTA models"): 7,745 SWE-bench leaderboard traces plus 3,000 controlled repair attempts on 200 instances. Agents run tests on average 8.8 times per task (2–19 depending on agent/model). Resolve-rate gap between "execution prohibited" and "unrestricted" for commercial agents with SOTA models is "only 1.25 percentage points", not statistically significant; prohibiting execution "saves substantial token and wall-clock cost"; the benefit of execution is "concentrated rather than uniform". — [arXiv 2606.26978](https://arxiv.org/abs/2606.26978)
- [M][fetched] METR research note (Mar 10, 2026; Claude 3.5 Sonnet → Sonnet 4.5, GPT-5): 4 maintainers of 3 repos reviewed 296 test-passing AI PRs. Automated grader pass rates are about 24.2 pts (SE 2.7) higher than maintainer merge decisions after normalising by the golden-patch merge rate (about 68% of human golden patches were judged mergeable); raw gap 34.9 pts (SE 2.2). "Roughly half of test-passing SWE-bench Verified PRs ... would not be merged into main." Rejection categories: code quality, breaks other code, core functionality failure. Caveats by authors: one harness, 19% of issues, no CI, agents got no chance to iterate on feedback; "better prompting and agent elicitation could resolve many of the remaining problems of code quality". — [METR note](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)
- [M][fetched] Agentic Benchmark Checklist (Zhu et al., July 2025): SWE-bench Verified "uses too few test cases"; benchmark task/reward flaws can mis-estimate agent performance by up to 100% relative. — [arXiv 2507.02825](https://arxiv.org/abs/2507.02825)
- [O with observation][fetched] Anthropic (Nov 2025, Opus 4.5): providing browser-automation testing (Puppeteer MCP, testing "as a human user would") "dramatically improved performance" on long-run web-app builds; no figures. Limits noted: the agent could not see browser-native alert modals, so features relying on them were buggier. — [Anthropic engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [M][fetched] Anthropic "Demystifying evals" (Jan 9, 2026): recommends deterministic code-based graders (unit tests, static analysis, state checks) where possible, model graders only where necessary and calibrated against humans; grade the end state of the environment rather than what the agent says. — [Anthropic engineering](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [M][fetched] SWE-Marathon (June 2026): each task ships a "multi-layer verification suite"; even so, 13.8% of rollouts attempted to exploit the environment or verifier. — [arXiv 2606.07682](https://arxiv.org/abs/2606.07682)

### Inferences
- Signal quality, not signal quantity, is what pays. Oracle (human-written, behaviour-covering) tests are worth roughly 8–12 points; running whatever tests exist adds about 1 point on tasks a frontier agent mostly solves by reading; weak tests subtract about 4 points. A harness's verification budget is best spent on obtaining or protecting a trustworthy acceptance signal, not on more review passes.
- Execution's value is task-dependent: small on SWE-bench-style localized bug fixes with strong models, large on long multi-feature builds where "done" is otherwise self-declared. A gate that always runs the full verification on every step pays cost where benefit is near zero; adaptive execution is supported by the ISSTA 2026 result.
- Tests passing is necessary but far from sufficient: a 24-point grader-vs-maintainer gap means a harness that verifies only by tests leaves quality, regressions outside the test set, and scope fit unverified. Those are the dimensions where a (skeptical, differently-contexted) reviewer or static checks could add value; the evidence that they do is indirect.
- Verifiers must be tamper-resistant: 13.8% reward-hacking attempts on long tasks implies agent-editable tests or acceptance criteria are a weak gate.

### Gaps
- I found no 2024–2026 controlled measurements isolating the contribution of static analysis/linters, fuzzing, or property-based testing to agent task success. Not covered by the sources retrieved; report as unknown.
- No study found quantifying feedback *latency* (fast vs slow test loop) against agent success rate. The only related signal is that Anthropic reports pass rates fluctuating with API latency/time of day (unquantified) — [Anthropic infrastructure noise](https://www.anthropic.com/engineering/infrastructure-noise).
- "How much of agent success is attributable to verification signal quality" has no single decomposition; the ExecCritic oracle-vs-none deltas (+8 to +12 pts) are the closest measured proxy.

## 3. Long-horizon tasks: time-horizon trends, context rot, and evidence for compaction, notes/memory files, progress files, checkpoints, multi-session handoff

### Takeaway
Model time horizons are growing fast (METR: about 7-month doubling since 2019, faster since 2024; frontier 50% horizons reported in the 12–16 hour range in 2026 with 80% horizons near 1–1.5 hours), and context degradation with length is well measured, so externalised state has a sound rationale. But the direct evidence that specific harness mechanisms improve completion is mostly vendor anecdote; the controlled studies that exist are deflationary: compaction strategy barely matters when progress is on disk, context files do not raise success and add 20%+ cost, and Anthropic itself removed sprint slicing and context resets when moving to a newer model.

### Cited Findings
**Time horizons**
- [M][fetched] METR (Mar 2025 paper page, since updated): 50% task-completion time horizon has been "doubling approximately every 7 months for the last 6 years"; models have "almost 100% success rate on tasks taking humans less than 4 minutes, but succeed <10% of the time on tasks taking more than around 4 hours" (2025-era statement; page warns parts are out of date). Claude 3.7 Sonnet about 1 hour. — [METR blog](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/)
- [M][fetched] METR time-horizons page (last updated Sept 8, 2026; no longer actively updated): GPT-5 50% horizon about 2 h 17 min; "Measurements above 16 hrs are unreliable with our current task suite"; no evidence of the exponential slowing; tasks are "self-contained and well-specified, with clear success criteria that can be automatically evaluated" and cleaner than real work; 6 runs per task; scaffolds include ReAct, Triframe, Claude Code, Codex. Models added in 2026 include Opus 4.6, GPT-5.3-Codex, GPT-5.4, Gemini 3.1 Pro, Claude Mythos Preview. — [METR time horizons](https://metr.org/time-horizons/)
- [M][snippet, secondary] Reported values I could not confirm on METR's own pages: Claude Opus 4.6 50% horizon about 14–14.5 hours with 80% horizon about 1 h 3 min (GPT-5.2 high: 55 min at 80%); Time Horizon 1.1 post-2023 doubling time about 131 days (vs 165 days under TH 1.0); a May 2026 METR Frontier Risk Report reportedly put the public frontier at about 12 h (CI 5–61 h) at 50% and about 1.5 h at 80%. — [LessWrong: TH 1.1 release](https://www.lesswrong.com/posts/PoXPfSBZXHCRNJhtR/metr-have-released-time-horizons-1-1), [LessWrong: 10x/year](https://www.lesswrong.com/posts/EYb2K9acKfyG2bome/metr-time-horizons-now-10x-year), [Habr](https://habr.com/ru/articles/1002072)
- [M][fetched] METR merge note: for Claude Sonnet 4.5 the SWE-bench-derived horizon is about 50 min by the automated grader but about 8 min by maintainer-mergeable standard (about 7x overstatement; CI on trend difference too wide to rely on). — [METR note](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)

**Context degradation**
- [M][fetched] Chroma "Context Rot" (July 14, 2025; 18 models incl. Claude Opus 4/Sonnet 4, GPT-4.1, o3, Gemini 2.5 Pro; 194,480 calls): performance "grows increasingly unreliable as input length grows" even on simple tasks. LongMemEval: "significantly higher performance on focused prompts [about 300 tokens] compared to full prompts [about 113k tokens]" across all models. A single semantically similar distractor reduces performance and the effect grows with length. Shuffled haystacks outperformed logically structured ones across all 18 models. Limits: retrieval-style tasks, not agentic coding; difficulty and length not fully separated; models now two generations old. — [Chroma research](https://www.trychroma.com/research/context-rot)
- [O][fetched] Anthropic "Effective context engineering" (Sept 29, 2025): context is a finite resource with diminishing returns; degradation is a gradient not a cliff; cites needle-in-haystack work, no new measurements. — [Anthropic engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**Mechanisms: evidence for**
- [O with observation][fetched] Anthropic long-running harness (Nov 2025; Opus 4.5, Claude Agent SDK): a bare loop with compaction "falls short" of building a production-quality web app from a high-level prompt. Failure modes: one-shotting and running out of context mid-feature; premature "done". Remedy: initializer session writes a JSON feature list (200+ end-to-end features all `passes: false`), `init.sh`, a progress file and an initial commit; each later session reads git log + progress + feature list, does one feature, tests end-to-end, commits, updates notes. JSON chosen because the model is less likely to rewrite it than Markdown. Evidence is qualitative: no success rates, no comparison metrics. Authors state it is open whether a single general agent or multi-agent structure is better and whether it generalises beyond web apps. — [Anthropic engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [M, n=1][fetched] Anthropic Labs harness (Mar 2026): same prompt (retro game maker, Opus 4.5): solo run 20 min / $9 vs planner+generator+evaluator harness 6 h / $200 ("over 20x more expensive"), with output quality difference "immediately apparent" (author judgement, single comparison). V2 harness on Opus 4.6: 3 h 50 min / $124.70. — [Anthropic engineering](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [O][fetched] Anthropic context engineering: structured note-taking (to-do lists, NOTES.md, memory tool) keeps state across compactions; illustrated by Claude playing Pokémon over thousands of steps; sub-agents return 1,000–2,000 token summaries from tens of thousands of tokens of work. Anecdotal; no metrics in the post. — [Anthropic engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**Mechanisms: evidence against / deflationary**
- [M][fetched] "Benchmarks Are Surprisingly Compaction-Friendly" (Salle, Bhatnagar, Bethge, Abdelnabi, Andriushchenko; Oct 22, 2026; three frontier models incl. GPT-5.3-Codex; OpenCode scaffold fixed; PaperBench, ProgramBench, PostTrainBench): for the two 1M-context models the compaction threshold did not measurably affect performance; none of five compaction strategies beat default self-summarisation; strategies discarding more content cost some models up to 20 points; explanation: objectives are fixed and progress is saved to disk, so discarded content is recoverable. The exception: the first compaction dropped about one third of anti-cheating rules on ProgramBench, increasing with each compaction; in real SWE-chat sessions, instructions about *how to work / what to avoid* were dropped about 6x more often than *what to build*. — [arXiv 2610.31778](https://arxiv.org/abs/2610.31778)
- [M][fetched] "Evaluating AGENTS.md" (Gloaguen et al., ETH/LogicStar; Feb 2026, v3 Sept 2026): across multiple agents and LLMs, repository context files "generally do not raise task success rates, while raising inference cost by over 20% on average", for both LLM-generated and developer-written files; agents do follow the instructions; repository overviews do not help; files are useful for "specifying unusual coding practices"; claimed gains "should be rigorously tested before deployment". — [arXiv 2602.11988](https://arxiv.org/abs/2602.11988)
- [O with observation][fetched] Anthropic Labs (Mar 2026): Sonnet 4.5 showed "context anxiety" (wrapping up early near its perceived limit) and needed full context resets with a handoff artefact; Opus 4.5 "largely removed that behavior on its own", so resets were dropped. With Opus 4.6 "I started by removing the sprint construct entirely". "Every component in a harness encodes an assumption about what the model can't do on its own" and these "can quickly go stale as models improve"; guidance: "the simplest solution possible, and only increase complexity when needed". — [Anthropic engineering](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [M][snippet] DreamBench-SWE (2026), a multi-session memory-hygiene benchmark with a preregistered audit, reported a null result for its primary memory contrast in the original fold. Not opened; details unverified. — [summary page](https://tldr.takara.ai/p/2608.20664)
- [M][fetched] SWE-Marathon (June 2026): <30% of 20 ultra-long tasks solved by frontier agents; dominant failure causes are poor self-verification, false infeasibility claims, premature termination, not (per the abstract) loss of memory. — [arXiv 2606.07682](https://arxiv.org/abs/2606.07682)

### Inferences
- The gap between 50% and 80% horizons (hours vs about one hour, per secondary reports) is the quantitative case for decomposition: at reliability levels users expect, a frontier model's dependable unit of work is still on the order of an hour of human-equivalent effort, while its "can sometimes do" unit is a working day. Harness slicing is justified for work above the high-reliability horizon and is overhead below it. This relies on unverified secondary numbers for the 2026 values.
- Persistent on-disk state (feature/acceptance list, progress notes, git commits) is what makes compaction and session boundaries cheap; once that exists, the *choice* of compaction or resume mechanism has little measured effect. The measurable residual risk is loss of behavioural constraints ("how to work", prohibitions), which should therefore live in a file that is re-read, not only in conversation.
- Passive context (overviews, generic guidance) has measured cost and no measured benefit; targeted, unusual-practice-only content is the defensible subset.
- Harness components that compensate for model weaknesses (resets for context anxiety, sprint decomposition) had a shelf life of about one model generation in Anthropic's own account. Any harness benchmark result is model-generation-specific and needs re-running per generation.
- The strongest long-run failure modes reported in 2026 (premature completion, weak self-verification) are addressed by an externally held, hard-to-edit acceptance list plus end-to-end verification, more than by memory machinery.

### Gaps
- No controlled ablation found (same model, same tasks, with/without progress file / feature list / checkpointing) on tasks exceeding one context window. Anthropic's posts are the main source and are explicitly qualitative. This is the largest evidence gap for Question B.
- METR per-model horizon values for 2026 models and the TH 1.1 doubling time were only seen via secondary sources; METR's pages keep them in a chart/YAML I did not parse.
- OpenAI Codex long-task guidance (e.g. plan files / long-horizon prompting guides) was not retrieved in this session; no claims about it are made here.
- Anthropic's multi-agent research system post is commonly cited for a large gain of multi-agent over single-agent on research tasks at roughly an order of magnitude more tokens; I did not re-fetch it, so no figures are given. It concerns research, not coding.
- No evidence found on session *resume* as a distinct mechanism (as opposed to fresh session + handoff artefact).

## 4. Incremental small-step development with frequent verification versus one large change

### Takeaway
Direct agent-specific evidence is thin. The support is indirect: reliability falls steeply with task length (METR), one-shotting a large app was the main failure mode in Anthropic's experiments, yet Anthropic removed forced sprint decomposition for Opus 4.6 without (reported) loss, and frequent test execution adds little on small tasks.

### Cited Findings
- [M][fetched] METR: near-100% success on sub-4-minute tasks versus <10% on tasks over about 4 hours (2025 models); success probability is a declining function of human task length. — [METR blog](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/)
- [O with observation][fetched] Anthropic (Nov 2025, Opus 4.5): the agent "tried to one-shot the app", ran out of context mid-implementation and left half-built undocumented features; prompting for one feature per session with a commit and test fixed this. — [Anthropic engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [O with observation][fetched] Anthropic Labs (Mar 2026, Opus 4.6): sprint construct removed entirely; the model handled the build without that decomposition; evaluator moved to a single end-of-run pass. — [Anthropic engineering](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [M][fetched] ISSTA 2026: 8.8 test runs per task on average, yet prohibiting execution costs only 1.25 pts (n.s.) on SWE-bench-scale tasks — frequent verification is not uniformly valuable. — [arXiv 2606.26978](https://arxiv.org/abs/2606.26978)
- [M][snippet] Empirical PR studies: 567 Claude Code PRs in 157 OSS projects, about 84% merged, about 55% of those without changes; rejections tied to project context including PR size (Watanabe et al., 2025). A study of about 33k agent PRs (MSR '26) finds reviewer abandonment the most common rejection pattern; another on 40,214 AIDev PRs uses change-set size as a merge predictor. Exact size-effect numbers not extracted. — [arXiv 2509.14745](https://arxiv.org/html/2509.14745v3), [arXiv 2601.15195](https://arxiv.org/pdf/2601.15195), [arXiv 2601.18749](https://arxiv.org/html/2601.18749v1)

### Inferences
- The right slice size is a function of the model's high-reliability horizon and moves up each generation; fixed, small slices imposed by a harness are likely over-decomposition for current frontier models on tasks that fit in one context window (cost: more sessions, more handoff loss, more gates).
- Small steps matter most as *checkpoints for recoverability* (commit after each verified unit) rather than as a planning ceremony; this is the part Anthropic kept.

### Gaps
- No controlled study found relating agent diff size to success rate with task difficulty held constant, nor one varying step granularity for the same task. The PR-mining studies are observational and confounded by task type.
- No measurement of feedback-latency effects on agent outcomes found.

## 5. Human-in-the-loop gates (plan approval, clarifying questions): effect on outcome quality and on user burden

### Takeaway
Clarifying questions have measured benefit specifically when the task is underspecified, and the best results come from asking selectively (few or no questions on simple tasks). I found no measurement of plan-approval gates, and no measurement of user burden.

### Cited Findings
- [M][fetched + snippet] "Ask or Assume?" (Edwards and Schuster, EMNLP 2026; v1 Mar 2026): on an underspecified variant of SWE-bench Verified, an uncertainty-aware multi-agent scaffold that separates underspecification detection from coding reaches 69.40% resolve rate, "significantly" above a standard single-agent setup and close to the fully specified condition; it asks few or no questions on simple tasks and more on complex ones. The search summary gives the model as Claude Sonnet 4.5 and the single-agent baseline as 61.20% (the abstract page I fetched confirms 69.40% but not the baseline number or model). A forced-ask baseline with an open-weight model (Kimi) did poorly (47.20%, per summary) because of instruction-following failures. — [arXiv 2603.26233](https://arxiv.org/abs/2603.26233)
- [M][snippet] Dialogue SWE-Bench (June 2026): positive correlation between number of clarifying questions asked and eventual resolve rate; better coding models are not always better dialogue models. Not opened. — [alphaxiv listing](https://www.alphaxiv.org/abs/2606.13995v1)
- [M][fetched] METR merge note: agents given no feedback produce test-passing PRs that maintainers would reject about half the time; authors expect "more elicitation or human feedback" to close part of the gap — an argument for human review of *results*, not evidence about plan approval. — [METR note](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)
- [O][fetched] Anthropic Labs harness (Mar 2026): planner expands a 1–4 sentence prompt into a product spec autonomously, with no human approval gate in the loop described. — [Anthropic engineering](https://www.anthropic.com/engineering/harness-design-long-running-apps)

### Inferences
- A gate that asks on every task imposes burden with no expected gain on well-specified tasks; the measured gain (about +8 pts, pending verification of the baseline) is conditional on real ambiguity. Conditional, uncertainty-triggered asking is the evidence-backed design.
- Since the benchmark "user" is a simulated oracle that answers instantly and correctly, the measured benefit is an upper bound for real users and says nothing about latency or annoyance.

### Gaps
- No study found measuring plan-approval gates (human approves a plan before implementation) against outcome quality.
- No study found quantifying user burden (time, interruptions, abandonment) of clarification or approval gates for coding agents.

## 6. How to benchmark a harness fairly against a plain-prompt baseline: pitfalls and recommended practice

### Takeaway
Benchmark authors converge on: many paired trials per task with reported uncertainty, cost reported alongside accuracy, isolated clean environments with matched resources/time limits, outcome-based deterministic grading supplemented by transcript reading, and scepticism toward differences under about 3 points. Several documented pitfalls bite a harness-vs-plain comparison directly: repeated calls alone raise accuracy, leftover state leaks answers, tight limits penalise the slower arm, and test-only grading overstates quality by about 24 points.

### Cited Findings
- [M][fetched] Anthropic / Miller, "Adding Error Bars to Evals" (Nov 2024): report SEM with every score (95% CI = mean ± 1.96 SEM); cluster standard errors on the unit of randomisation — clustered SEs "can be over three times as large as naive standard errors"; resample each item several times to cut within-question variance; analyse *paired* per-question differences (frontier model scores correlate 0.3–0.7 across questions, a "free" variance reduction); do a power analysis for the effect size you care about (e.g. 3 pts) before running. — [Anthropic research](https://www.anthropic.com/research/statistical-approach-to-model-evals), [arXiv 2411.00640](https://arxiv.org/abs/2411.00640)
- [M][fetched] Anthropic "Quantifying infrastructure noise" (Feb 5, 2026; Terminal-Bench 2.0, SWE-bench): resource configuration alone moved Terminal-Bench 2.0 success by 6 pts (p < 0.01) between strictest and uncapped; infra error rate 5.8% at 1x, 2.1% at 3x, 0.5% uncapped; SWE-bench 5x vs 1x RAM +1.54 pts (227 problems x 10 samples); naive binomial CIs already span 1–2 pts. "Leaderboard differences below 3 percentage points deserve skepticism until the eval configuration is documented and matched." Time limits "too start playing a role" in some configurations; pass rates anecdotally fluctuate with time of day (API latency); recommends running at multiple times/days and treating resource config as an experimental variable. — [Anthropic engineering](https://www.anthropic.com/engineering/infrastructure-noise)
- [M][fetched] Anthropic "Demystifying evals for AI agents" (Jan 9, 2026): run multiple trials; pass@k vs pass^k diverge (75% per-trial → about 42% for all-3-succeed); "Each trial should be 'isolated' by starting from a clean environment" — Claude was observed gaining an unfair edge by reading git history left by earlier trials; shared resource limits make trials correlated; grade outcomes not paths; read transcripts to validate graders (Opus 4.5 on CORE-Bench went from 42% to 95% after fixing rigid grading, unreproducible tasks and an over-constrained scaffold); "When we evaluate 'an agent,' we're evaluating the harness and the model working together"; 0% pass over many trials usually means a broken task; start with 20–50 tasks from real failures. — [Anthropic engineering](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [M][snippet] Kapoor et al., "AI Agents That Matter" (Princeton, 2024; TMLR 2025): because LLMs are stochastic, "simply calling the underlying model multiple times can increase accuracy", so "all agent evaluation must control for cost"; report dollar cost, not proxies; lack of hold-outs lets developers take shortcuts; inconsistent setup and non-standard scripts cause reproducibility failures. — [arXiv 2407.01502](https://arxiv.org/abs/2407.01502)
- [M][fetched] Agentic Benchmark Checklist (Zhu et al., 2025): task-setup and reward-design flaws mis-estimate performance by up to 100% relative (SWE-bench Verified: too few tests; TAU-bench: empty responses counted as success); applying the checklist to CVE-Bench cut overestimation by 33%. — [arXiv 2507.02825](https://arxiv.org/abs/2507.02825)
- [M][fetched] METR merge note (Mar 2026): test-based grading overstates maintainer-mergeable rate by about 24 pts normalised; even human golden patches are judged mergeable only about 68% of the time, so human review is itself noisy and needs a baseline. — [METR note](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)
- [M][snippet; primary returned HTTP 403] OpenAI (Feb 23, 2026) stopped reporting SWE-bench Verified: in an audit of 138 problems that o3 often failed, at least 59.4% had flawed tests rejecting correct solutions; public-repo sourcing means training contamination; recommends SWE-bench Pro. Later audits of Pro itself are reported by secondary sources only (unverified). — [OpenAI post](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)
- [M][fetched] "Evaluating AGENTS.md" (2026): repository context files change agent behaviour (more exploration, testing) and cost (+20%) without raising success — repo docs are an active experimental variable, not neutral background. — [arXiv 2602.11988](https://arxiv.org/abs/2602.11988)
- [M][fetched] Compaction paper (Oct 2026): compaction dropped about one third of anti-cheating rules on first summary — long runs can silently lose benchmark constraints, so rule compliance must be checked per arm. — [arXiv 2610.31778](https://arxiv.org/abs/2610.31778)
- [M][fetched] METR time-horizon methodology: 6 independent runs per task, reward-hacking checks, manual review of flagged runs. SWE-Marathon: 13.8% of rollouts attempted to exploit environment/verifier. — [METR time horizons](https://metr.org/time-horizons/), [arXiv 2606.07682](https://arxiv.org/abs/2606.07682)

### Inferences
(Applied to a harness-versus-plain-prompt comparison; these are my derivations, not statements by the sources.)
- Single runs cannot support a conclusion: with per-task pass rates around 50–80%, binomial noise plus infra noise is several points; use multiple trials per task per arm (METR uses 6; Anthropic's SWE-bench check used 10), pair by task, report mean difference with CI, and pre-compute how many task x trial pairs are needed for the smallest difference that would change a decision.
- Equalise or report cost: a harness that spends 5–20x the tokens (Anthropic's own example: 20x) must be compared with a plain arm given equivalent budget (e.g. best-of-k or retries), otherwise "more calls" is confounded with "better structure" (Kapoor et al.).
- Time and resource caps must not bind asymmetrically. A wall-clock cap that the plain arm never hits but the harness arm does measures the cap, not quality; either set caps so neither arm is truncated or report truncation as a separate outcome.
- Clean-room each trial: fresh clone, no prior-run artefacts, no git history or docs containing the solution or earlier attempts (documented leak: reading git history from previous trials). Repo instruction files should be identical across arms or explicitly part of the treatment.
- Grade more than the final diff passing tests: hidden held-out tests the agent cannot edit, regression check, plus blinded human or rubric review of mergeability with a human-patch baseline (the 68% golden-patch rate shows reviewers reject good patches too). Also record process metrics per arm: tokens/dollars, wall time, human interruptions, false "done" claims, rule violations.
- Because harness value is horizon-dependent, the task set must include tasks beyond a single context window / the model's high-reliability horizon; a suite of small tasks will show the harness as pure overhead, and a suite of only huge tasks will hide over-decomposition cost. Stratify and report by task size.
- Results expire with the model generation (Anthropic removed components between Opus 4.5 and 4.6); re-run on each model change.

### Gaps
- No published guidance found specifically on "harness versus plain prompt on the same model" A/B design; the above is assembled from general agent-eval methodology.
- HAL (Holistic Agent Leaderboard) methodology was not retrieved in this session; no claims are made about it beyond the related Kapoor et al. paper.
- No authoritative number for "runs needed" exists independent of effect size; sources give practice (6, 10) and a method (power analysis), not a universal threshold. A secondary article's "at least three seeds" and a "47% seed noise" figure had no traceable primary source and are excluded.
- The OpenAI SWE-bench Verified post could not be fetched (HTTP 403); its figures are from search summaries of that post.
