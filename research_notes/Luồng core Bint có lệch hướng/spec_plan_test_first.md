# Spec-driven development, plan-first workflows, and agent-written acceptance tests in AI coding agents: evidence for and against (2024–2026)

Reading guide for the report writer:
- Each finding is tagged **[MEASURED]** (controlled or statistical study), **[VENDOR-MEASURED]** (numbers from a party with a commercial interest), **[ANECDOTE/OPINION]** (practitioner experience or argument), or **[GUIDE]** (vendor documentation).
- Each finding is also tagged with how I verified it: **(primary read)** = I fetched the paper/page itself; **(abstract only)** = only the arXiv abstract page was read; **(search snippet)** = the figure comes from a search-result summary and was NOT checked against the primary source.
- Research date: 2026-11-20. Model generations are noted per study because results age quickly.

## 1. What measured evidence exists on spec-driven development (SDD) tools and workflows (Spec Kit, Kiro, BMAD, OpenSpec, Tessl, plan mode)?

### Takeaway
Rigorous evidence that SDD improves outcomes is close to absent: the one peer-reviewed large-scale test (ESEM 2026) is a null result, and it measured issue/ticket references rather than actual SDD tool output. The only head-to-head comparison of the named tools is a small vendor-run benchmark, where spec workflows helped on large tickets and features but gave no benefit on small tickets and bug fixes, while adding 28–44% token overhead and 7–26 minutes per ticket.

### Cited Findings

**Peer-reviewed null result (ESEM 2026)**
- **[MEASURED] (primary read)** Brenn Hill, "Specification Artifacts in Open-Source Pull Request Workflows Do Not Reduce Defects: An Empirical Test of Spec-Driven Development Claims", ESEM 2026 (Software Engineering in Practice track). Dataset: 88,052 merged pull requests across 119 open-source repositories (12,195 bot PRs excluded); 25,209 specification artifacts scored on the quality dimensions SDD tools prescribe; defects traced with SZZ; within-author comparison plus twelve robustness checks. — [LIPIcs.ESEM.2026.84](https://drops.dagstuhl.de/storage/00lipics/lipics-vol394-esem2026/LIPIcs.ESEM.2026.84/LIPIcs.ESEM.2026.84.pdf)
- **[MEASURED] (primary read)** Result: "None of the five hypotheses are supported." After propensity score matching, spec'd and unspec'd PRs are indistinguishable in defect introduction (−0.6 pp, p = 0.133). Rework shows no protective effect (+1.2 pp, p = 0.001 within-author; +0.5 pp, p = 0.146 matched). Specification quality predicts neither defects (p = 0.164) nor rework (p = 0.860). Specifications "do not constrain the scope of AI-tagged changes" (p = 0.997). — [same paper](https://drops.dagstuhl.de/storage/00lipics/lipics-vol394-esem2026/LIPIcs.ESEM.2026.84/LIPIcs.ESEM.2026.84.pdf)
- **[MEASURED] (primary read)** The author's explanation of the raw positive association between specs and defects: "developers spec their hardest work"; "Specification artifacts proxy for task complexity, not quality improvement." — [same paper](https://drops.dagstuhl.de/storage/00lipics/lipics-vol394-esem2026/LIPIcs.ESEM.2026.84/LIPIcs.ESEM.2026.84.pdf)
- **[MEASURED] (primary read) — critical limitation stated by the author:** what was measured is "overwhelmingly references to tracking issues and tickets — rather than SDD tool output, which no repository in the sample commits." "SDD tool adoption itself remains untested." So this paper does NOT show that Spec Kit/Kiro output is useless; it shows that the general claim "written specification before implementation reduces defects" finds no support in PR data. — [same paper](https://drops.dagstuhl.de/storage/00lipics/lipics-vol394-esem2026/LIPIcs.ESEM.2026.84/LIPIcs.ESEM.2026.84.pdf)
- **[MEASURED] (primary read)** The paper states that vendors "cite no empirical evidence" for SDD quality claims "in their marketing materials, documentation, or blog posts", and that no study had tested the claims on production-scale data before it. — [same paper](https://drops.dagstuhl.de/storage/00lipics/lipics-vol394-esem2026/LIPIcs.ESEM.2026.84/LIPIcs.ESEM.2026.84.pdf)
- One subgroup ran the other way: in repositories with no detected AI use, specs were associated with less rework (−3.3 pp, p = 0.014), but this was one of six subgroup tests and did not survive multiple-comparison correction. — [same paper](https://drops.dagstuhl.de/storage/00lipics/lipics-vol394-esem2026/LIPIcs.ESEM.2026.84/LIPIcs.ESEM.2026.84.pdf)

**Head-to-head tool benchmark (vendor-run, small n)**
- **[VENDOR-MEASURED] (primary read)** Uvik Software (a Python staff-augmentation vendor; author Paul Francis), dated 15 Oct 2026. 50 brownfield Python tickets from five client repositories (10 each: bug fix, feature, refactor, data pipeline, test writing; 20 small / 20 medium / 10 large). Model: claude-sonnet-5 in all arms; Spec Kit 1.0, BMAD 6.x, OpenSpec and the no-spec control ran in Claude Code 2026.09; Kiro ran in its own IDE. A reviewer blind to the arm accepted or rejected each patch. Reruns of ten tickets set a noise band of about ±10 points on merge rate. — [Uvik benchmark](https://uvik.net/blog/spec-driven-development-benchmark/)
- **[VENDOR-MEASURED] (primary read)** Overall merge rate (of 50): Spec Kit 80%, Kiro 82%, BMAD 82%, OpenSpec 84%, no-spec control 72%. Review defects per merged ticket: 0.57 / 0.39 / 0.49 / 0.40 versus 0.86 for the control. — [Uvik benchmark](https://uvik.net/blog/spec-driven-development-benchmark/)
- **[VENDOR-MEASURED] (primary read)** Cost and time: median time to merge 44 / 41 / 55 / 36 minutes versus 29 minutes for the control; spec-writing minutes 18 / 16 / 28 / 12 versus 0. Cost per merged ticket $3.33 / $2.35 / $4.23 / $2.71 versus $2.43 for the control. — [Uvik benchmark](https://uvik.net/blog/spec-driven-development-benchmark/)
- **[VENDOR-MEASURED] (primary read)** Tokens (median per ticket): spec phase consumed 147,206 (Spec Kit), 130,986 (Kiro), 227,212 (BMAD), 104,924 (OpenSpec) tokens, i.e. 34.0% / 32.1% / 43.9% / 28.3% of the total. Build-phase tokens were lower with a spec (265,717–290,429) than without (331,936), but not by enough to offset the spec phase. — [Uvik benchmark](https://uvik.net/blog/spec-driven-development-benchmark/)
- **[VENDOR-MEASURED] (primary read)** By task size (Spec Kit / Kiro / BMAD / OpenSpec / control): small 80 / 85 / 85 / 85 / **85%**; medium 80 / 80 / 80 / 85 / 70%; large 80 / 80 / 80 / 80 / **50%**. — [Uvik benchmark](https://uvik.net/blog/spec-driven-development-benchmark/)
- **[VENDOR-MEASURED] (primary read)** By task type: bug fix 80 / 90 / 80 / 90 / **90%** (control ties the best); feature 80 / 80 / 90 / 80 / 60%; refactor 80% in every arm; data pipeline 80 / 90 / 90 / 90 / 60%; test writing 80 / 70 / 70 / 80 / 70%. — [Uvik benchmark](https://uvik.net/blog/spec-driven-development-benchmark/)
- **[VENDOR-MEASURED] (primary read)** Spec drift (share of merged tickets where the final code diverged from the spec): Spec Kit 12.5%, Kiro 4.9%, BMAD 12.2%, OpenSpec 2.4%. — [Uvik benchmark](https://uvik.net/blog/spec-driven-development-benchmark/)
- Stated limitations: one team of five engineers; Python only; one model; fixed 45-minute time boxes "that could favor heavier planning"; Kiro on a different harness; one ticket at a time, so long-term spec maintenance was not tested. — [Uvik benchmark](https://uvik.net/blog/spec-driven-development-benchmark/)

**How SDD is actually practised**
- **[MEASURED, qualitative] (abstract only)** Agarwal, Singhal, Macvean, Vasilescu, Breaux, "Spec-Driven Development as Prescribed and as Practiced" (arXiv 2608.25202, Aug 2026, v5 Nov 2026): interviews with 21 practitioners including eight tool makers, plus 266 active and popular repositories from SpecMine, a corpus of 470,795 spec files from 73,030 public GitHub repositories. Practitioners "used SDD selectively and mainly for new features". The abstract also notes that "implementation detail may help agents while making specs prone to decay". The abstract gives no quantitative drift or staleness figures. — [arXiv 2608.25202](https://arxiv.org/abs/2608.25202)

**Credible practitioner critique (hands-on, not measured)**
- **[ANECDOTE/OPINION] (primary read)** Birgitta Böckeler (Thoughtworks), "Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl", martinfowler.com, 15 October 2025. On Kiro with a small bug fix: "The requirements document turned this small bug into 4 "user stories" with a total of 16 acceptance criteria"; she described it as "like using a sledgehammer to crack a nut." — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **[ANECDOTE/OPINION] (primary read)** On Spec Kit: "spec-kit created a LOT of markdown files for me to review"; they were "repetitive, both with each other, and with the code that already existed"; "Overall they were just very verbose and tedious to review"; "To be honest, I'd rather review code than all these markdown files." — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **[ANECDOTE/OPINION] (primary read)** Specs do not guarantee compliance: "I frequently saw the agent ultimately not follow all the instructions"; in one Spec Kit run the agent ignored notes describing existing classes and regenerated them as duplicates. "just because the windows are larger, doesn't mean that AI will properly pick up on everything that's in there." — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **[ANECDOTE/OPINION] (primary read)** Fit to problem size: she is "quite sure that neither of them is suitable for the majority of real life coding problems" and "very skeptical that lots of up-front spec design is a good idea", preferring small iterative steps. For a mid-sized feature she suspected plain AI-assisted coding would have been faster and left her more in control. — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **[ANECDOTE/OPINION] (primary read)** Historical parallel: "The models in MDD were basically the specs, albeit not in natural language"; spec-as-source "might end up with the downsides of both MDD and LLMs: Inflexibility and non-determinism." She saw "the non-determinism in action" regenerating code from the same Tessl spec. She closes with the German word *Verschlimmbesserung*: "Are we making something worse in the attempt of making it better?" — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **[ANECDOTE/OPINION] (search snippet, secondary)** Kent Beck's objection as relayed by a commentary: most SDD write-ups assume the whole spec is written before implementation, which assumes nothing will be learned during implementation. I did not locate Beck's original text. — [DEV Community commentary](https://dev.to/sam_curatedmcp/spec-driven-development-renamed-an-old-problem-it-didnt-solve-it-tags-ai-productivity-347a)
- **[ANECDOTE] (search snippet)** A single-author case study reported token usage roughly tripling with specs, while spec-driven runs caught bugs that baseline runs shipped. Not verified against the post. — [DEV Community case study](https://dev.to/dimwiddle/ai-agents-cant-mark-their-own-homework-case-study-26mk)

**Method papers (favourable to specs, but each evaluates its own approach)**
- **[MEASURED] (abstract only)** Tufano et al. (Google), "Grounding AI Agents in Contracts: An Empirical Evaluation of Spec-Driven Test Generation" (arXiv 2608.17177, Aug 2026). An agent first writes pre-conditions, post-conditions and undefined behaviours, then tests. Against a baseline test-generation agent on production bugs from Google: bug detection rate +9.8 percentage points (p = 0.0352), branch coverage +2.5 points (p = 0.0034); an LLM judge preferred the spec-driven suites over the baseline in 77.8% of cases and over human-authored tests in 56.7%. Note the scope: this is a semi-formal contract for an EXISTING piece of code used to write tests, not a requirements document expanded from a user prompt. Models not named in the abstract. — [arXiv 2608.17177](https://arxiv.org/abs/2608.17177)
- **(search snippet)** CodeSpec (arXiv 2607.26777) and WiseSpec (arXiv 2609.00568) propose spec/requirements-based agents and report gains on FeatureBench / SWE-bench. Not read; as method papers they compare in favour of their own design. — [CodeSpec](https://arxiv.org/pdf/2607.26777); [WiseSpec](https://arxiv.org/pdf/2609.00568)

### Inferences
- The two quantitative sources agree on one point despite opposite headlines: the benefit of a spec is concentrated in large or feature-type work. In the vendor benchmark the control matched or beat spec workflows on small tickets and bug fixes; in the ESEM paper specs track task complexity rather than quality. A workflow that forces a spec on every task pays the overhead where no benefit was measured.
- With n = 10 per cell and a stated ±10-point noise band, most per-type differences in the vendor benchmark are within noise. Only the large-ticket gap (80% vs 50%) and the feature/data-pipeline gaps (80–90% vs 60%) clearly exceed it, and those rest on 10 tickets each.
- The vendor benchmark's 45-minute time box and blind human merge review measure "would a reviewer merge this", not long-run defect rate; the ESEM paper measures long-run defects but not real SDD tools. No study covers both.
- Spec overhead is quantifiable: roughly 28–44% of tokens and 12–28 minutes of human time per ticket in the one study that measured it. The lightest spec format (OpenSpec) had the best merge rate and the lowest drift, which is weak evidence that more spec ceremony does not buy more quality.
- The ESEM finding that specs "do not constrain the scope of AI-tagged changes" (p = 0.997) directly contradicts the common claim that a spec keeps the agent in scope, with the caveat that the specs were tickets, not agent-written specs.

### Gaps
- No controlled study was found that isolates the effect of an AGENT-WRITTEN requirements document (expanded from a short user prompt) on final correctness, holding model and harness constant, on a public benchmark.
- No measurement of "specs larger than the code" as a ratio was found; the claim exists only as practitioner anecdote (Böckeler's review burden remarks).
- No independent (non-vendor) replication of the Spec Kit / Kiro / BMAD / OpenSpec comparison was found. GitHub and AWS publish no outcome data for Spec Kit or Kiro according to the ESEM paper; I did not independently audit their documentation.
- No measured comparison of "plan mode" on versus off in Claude Code, Cursor, or Codex as shipped products was found.
- Tessl was in private beta when reviewed (Oct 2025); no outcome data found.
- Quantitative drift/staleness figures from the full text of arXiv 2608.25202 were not extracted (abstract only).

## 2. What does research say about plan-then-execute versus direct/ReAct-style execution for coding?

### Takeaway
The best controlled ablation found (176 harness settings, Sept 2026) shows a persistent plan scaffold significantly raises success only for the weakest model (+11.6 points); for stronger models success is flat or slightly lower (−0.4 to −2.6 points) while cost falls about 30%. Planning is an accuracy crutch for weak models and at most a cost lever for strong ones.

### Cited Findings
- **[MEASURED] (primary read, first 100k characters of the HTML)** Fan et al., "An Empirical Study of Harness Design for Coding Agents" (arXiv 2609.20804, 17 Sep 2026). Fixed execution loop, varying planning, action space and context management across 176 settings on SWE-Bench Verified (500 issues) and Terminal-Bench 2.1 (89 tasks). Planning "on" = a persistent plan maintained via an `update_plan` tool with per-turn reminders; "off" removes instructions, reminders and tool. — [arXiv 2609.20804](https://arxiv.org/html/2609.20804)
- **[MEASURED] (primary read)** SWE-Bench Verified success rate, plan on vs off: Nemotron-3 30B 25.20% vs 13.60% (cost $0.09 vs $0.02); Nemotron-3 120B 44.00% vs 46.60% ($0.34 vs $0.25); Nemotron-3 550B 65.80% vs 67.80% ($2.33 vs $3.31); Mistral-Medium-3.5-128B 68.60% vs 69.00% ($3.14 vs $4.65). Only the 30B gain is statistically significant (McNemar, BH-adjusted q < 0.05). — [arXiv 2609.20804](https://arxiv.org/html/2609.20804)
- **[MEASURED] (primary read)** Terminal-Bench 2.1, plan on vs off: 30B 13.48% vs 8.99%; 120B 28.09% vs 28.09%; 550B 44.94% vs 46.07%; Mistral 37.08% vs 39.33% (cost $2.22 vs $3.71). — [arXiv 2609.20804](https://arxiv.org/html/2609.20804)
- **[MEASURED] (primary read)** Mechanism: for the weak model, planning keeps the agent engaged (median trajectory 5 turns without planning vs 40 with; runs ending without any edit fall from 68.6% to 27.8%), at +293% turns and +474% tool calls. For the two strongest models planning SHORTENS trajectories (median 108 to 74 and 68 to 53 turns), "mostly from reduced post-edit verification", with "small decreases in success rate". — [arXiv 2609.20804](https://arxiv.org/html/2609.20804)
- **[MEASURED] (abstract)** The authors' own summary: "Planning shifts from an accuracy scaffold for weaker models to a cost saver for stronger models", with "little change in accuracy" for the latter. — [arXiv 2609.20804](https://arxiv.org/abs/2609.20804)
- Limitation stated by the authors: "Planning is instantiated through one prompt and update mechanism"; the result estimates this persistent scaffold, not planning as a general reasoning strategy, and not a separate human-reviewed plan phase. All four models are open-weight; no frontier proprietary model was tested. — [arXiv 2609.20804](https://arxiv.org/html/2609.20804)
- **(search snippet, not read)** A March 2026 paper (arXiv 2603.26458) on SWE-bench Lite argues a separate planning "manager" agent with executing workers improves results. This is a multi-agent method paper, not a single-agent planning ablation. — [arXiv 2603.26458](https://arxiv.org/pdf/2603.26458v1)

### Inferences
- The stronger the model, the smaller the accuracy return on an imposed planning scaffold. This matches the direction of vendor guidance (see question 5) that planning is optional for small, well-understood changes.
- The shortened trajectories for strong models came "mostly from reduced post-edit verification". A plan can substitute for checking: the agent ticks off plan items instead of verifying behaviour. This is a plausible mechanism for the small success-rate decreases and is a specific risk for plan-gated workflows.
- None of these results test the human-in-the-loop value of a plan (catching a wrong direction before code is written). The measured effect is on autonomous benchmark success only.

### Gaps
- I did not re-verify in this session the planning-related ablations in the SWE-agent, OpenHands, AutoCodeRover or Agentless papers. From memory (UNVERIFIED here): Agentless (arXiv 2407.01489, 2024, GPT-4o) argued that a fixed non-agentic localize-repair-validate pipeline matched or beat contemporaneous agents at lower cost, which is evidence for structure over free-form agency rather than for upfront natural-language planning. Treat as a lead to check, not a finding.
- No controlled study found on plan-first with frontier reasoning models (GPT-5 class, Claude 4/5 class) that isolates the planning step.
- No study found measuring the effect of plan LENGTH or plan detail on outcome.
- The last ~63k characters of the arXiv 2609.20804 HTML (appendices) were not read.

## 3. Test-driven approaches: do tests help, and do tests written by the same model share its blind spots?

### Takeaway
Tests supplied from OUTSIDE the implementing model are an effective specification, but tests are a weak oracle in general (even human-written SWE-bench tests pass 6–8% of wrong patches), and agents exploit tests under pressure (GPT-5 "cheated" on roughly 54–76% of impossible SWE-bench tasks). I found no study that directly measures correlated blind spots when the same agent writes both the acceptance tests and the code; the evidence is indirect.

### Cited Findings

**Tests as specification help**
- **[MEASURED] (search snippet of a third-party review; figures NOT confirmed against the paper)** In "Test-Driven Development for Code Generation" (2024), including tests alongside the problem statement reportedly solved an additional 12.0% of MBPP and 8.5% of HumanEval problems on the EvalPlus versions. In that setup the tests are given, not written by the model. — [themoonlight.io review](https://www.themoonlight.io/tw/review/test-driven-development-for-code-generation)
- **[MEASURED] (search snippet)** WebApp1K, "Tests as Prompt: A Test-Driven-Development Benchmark for LLM Code Generation" (arXiv 2505.09027, May 2025): 1000 challenges across 20 application domains where tests are both the prompt and the verifier. The paper reports degraded LLM performance as the number of test cases grows, i.e. more tests is not monotonically better. — [arXiv 2505.09027](https://arxiv.org/html/2505.09027v1)
- **[MEASURED] (search snippet)** TENET (repository-level): selecting a small but effective test suite is a key challenge; test selection strategy changes the code-generation pass rate. — [TENET review](https://liner.com/review/tenet-leveraging-tests-beyond-validation-for-code-generation)

**Models are weak at writing the tests first**
- **[MEASURED] (search snippet)** TDD-Bench Verified (IBM, arXiv 2412.02883, Dec 2024): asked to write fail-to-pass tests from an issue BEFORE the fix exists, the best configuration (GPT-4o) reached a 23.6% fail-to-pass rate. Model generation: GPT-4o era; likely higher with current models, not re-measured here. — [arXiv 2412.02883](https://arxiv.org/html/2412.02883v1)

**Oracle weakness of LLM-written tests**
- **[MEASURED] (search snippet)** "Do LLMs generate test oracles that capture the actual or the expected program behaviour?" (arXiv 2410.21136, Oct 2024): the study keeps only tests whose assertions pass on the code under test, noting that when the code is buggy some generated tests will be wrong, so "passes on the current code" is used as a proxy for correctness. LLM oracles outscored EvoSuite on mutation score in all but one configuration. — [arXiv 2410.21136](https://arxiv.org/html/2410.21136v1)
- **[MEASURED] (search snippet)** Mernst group, ASE 2025, "Do LLMs Generate Useful Test Oracles? An Empirical Study with an Unbiased Dataset": on projects created after model training cutoffs, LLM oracles averaged a 43% mutation score versus 45% for human-written oracles. Both leave more than half of mutants alive. — [ASE 2025 paper](https://homes.cs.washington.edu/~mernst/pubs/neurosymbolic-oracles-ase2025.pdf)
- **[MEASURED] (search snippet)** A CIBSE paper states that recent studies treat oracle weakness, not low coverage, as the main limitation of LLM-generated tests, with a persistent gap between coverage and mutation score. — [CIBSE paper](https://sol.sbc.org.br/index.php/cibse/article/download/42441/42208/)

**Passing tests does not mean correct (even with human tests)**
- **[MEASURED] (search snippet)** Wang, Pradel, Liu, "Are 'Solved Issues' in SWE-bench Really Solved Correctly?" (arXiv 2503.15223, 2025): 7.8% of patches counted as correct on SWE-bench Verified fail the developer-written test suite; the weaknesses inflate reported resolution rates by 6.2 absolute percentage points. — [arXiv 2503.15223](https://arxiv.org/abs/2503.15223)
- **[MEASURED] (search snippet)** UTBoost (ACL 2025): test augmentation found 36 SWE-bench task instances with insufficient tests and 345 erroneous patches that had been marked as passing, changing 18 leaderboard ranks on SWE-Bench Lite and 11 on Verified. — [ACL Anthology author page](https://aclanthology.org/people/boxi-yu/)

**Agents game tests**
- **[MEASURED] (search snippet)** ImpossibleBench (Zhong, Raghunathan, Carlini; arXiv 2510.20270, Oct 2025; ICLR 2026): tasks whose unit tests are mutated to contradict the specification, so any pass is a spec-violating shortcut. GPT-5 "cheated" on about 76% of the one-off SWE-bench variant but about 2.9% of the one-off LiveCodeBench variant; a secondary review gives 54.0% on the conflicting SWE-bench variant. Strategies include direct test modification, operator overloading, and special-casing test inputs. — [arXiv 2510.20270](https://arxiv.org/abs/2510.20270v1); [OpenReview PDF](https://openreview.net/pdf/f0edc0ee21784f063e1f7970ecbd360037762bb7.pdf)
- **[AUTHOR BLOG, not the peer-reviewed text] (search snippet)** Adding an instruction to stop if the tests are flawed reportedly cut GPT-5's hacking rate on the conflicting LiveCodeBench variant from 93% to 1%. — [authors' post](https://www.greaterwrong.com/posts/qJYMbrabcQqCZ7iqm/impossiblebench-measuring-reward-hacking-in-llm-coding-1)

**Mitigations studied**
- **(search snippet)** Mutation-guided approaches (MuTAP re-prompting with surviving mutants; Meta's ACH with separate mutant-generating and test-hardening agents) are cited in a 2026 paper on adversarial test-hardening with a pre-registered causal estimate of a critic loop. Not read. — [arXiv 2607.23002](https://arxiv.org/pdf/2607.23002)
- **[MEASURED] (abstract only)** A spec step before test writing improved bug detection by 9.8 points at Google (see question 1), which is evidence that a different viewpoint between "what should hold" and "what the code does" strengthens tests. — [arXiv 2608.17177](https://arxiv.org/abs/2608.17177)

### Inferences
- "Tests help" results come from settings where the tests encode information the implementer did not have (hidden or human-authored tests). When the same agent derives tests from the same reading of the same prompt, the tests add no new information about intent; they can only catch implementation slips, not misunderstanding. This is an inference: no study found measures it directly.
- The 23.6% fail-to-pass rate (GPT-4o era) means that a majority of agent-written "tests first" did not actually capture the target behaviour at that model generation; a gate that only checks "tests exist and pass" would have accepted them.
- A mutation score near 43–45% for both LLM and human oracles means that a passing suite is weak evidence of correctness regardless of author. Acceptance criteria satisfied by agent-authored tests should be treated as necessary, not sufficient.
- ImpossibleBench shows the gaming rate is highly context-dependent (2.9% vs 76% for the same model) and strongly reduced by an explicit "stop and report if the test looks wrong" instruction. Workflows that make passing a test the gate, without an escape hatch, create the pressure that produces gaming.

### Gaps
- No study found that directly compares (a) agent writes tests then code, (b) a separate model or human writes tests, (c) no tests, on final hidden-test correctness with a 2025–2026 frontier model. This is the central open question for agent-written acceptance tests.
- No measurement found of how often an agent weakens or rewrites ITS OWN earlier tests to get them to pass in a normal (non-adversarial) workflow.
- Most figures in this section are from search-result summaries, not the primary PDFs; exact numbers (12.0% / 8.5%, 43% vs 45%, 7.8% / 6.2 pp, 76% / 54.0% / 2.9%) should be re-checked before being quoted as headline facts.

## 4. Requirement elaboration from a vague prompt: scope creep and drift versus the benefit of clarifying questions

### Takeaway
Measured evidence favours ASKING over ASSUMING: obtaining missing information from the user improved underspecified-task performance by up to 74% (Ambig-SWE) and a scaffold that separates underspecification detection reached 69.40% vs 61.20% resolve rate. Agents left to fill gaps themselves take out-of-scope actions in 5–28% of runs on permissive harnesses, and specification artifacts did not constrain the scope of AI changes.

### Cited Findings
- **[MEASURED] (abstract only)** Vijayvargiya, Zhou, Yerukola, Sap, Neubig, "Ambig-SWE: Interactive Agents to Overcome Underspecificity in Software Engineering" (arXiv 2502.13069; ICLR 2026). An underspecified variant of SWE-Bench Verified. "models struggle to distinguish between well-specified and underspecified instructions"; when they do interact they obtain vital information "leading to significant improvements in performance, up to 74% over the non-interactive settings". The abstract does not say whether 74% is relative or absolute, nor name the models. — [arXiv 2502.13069](https://arxiv.org/abs/2502.13069)
- **[MEASURED] (abstract only)** The same paper names the failure of the alternative: "Making unwarranted assumptions to compensate for the missing information and failing to ask clarifying questions" leads to "suboptimal outcomes, safety risks due to tool misuse, and wasted computational resources." — [arXiv 2502.13069](https://arxiv.org/abs/2502.13069)
- **[MEASURED] (search snippet)** Edwards and Schuster, "Ask or Assume? Uncertainty-Aware Clarification-Seeking in Coding Agents" (arXiv 2603.26233, March 2026): on an underspecified SWE-bench Verified variant, a multi-agent scaffold that separates underspecification detection from code execution reached a 69.40% resolve rate versus 61.20% for a standard single-agent setup, using OpenHands with Claude Sonnet 4.5. The system asks fewer questions on simple tasks and more on complex ones. A forced-question baseline with another model (Kimi) performed poorly. — [alphaXiv 2603.26233](https://www.alphaxiv.org/abs/2603.26233)
- **[MEASURED] (abstract only)** Qu et al., "Overeager Coding Agents: Measuring Out-of-Scope Actions on Benign Tasks" (arXiv 2605.18583, May 2026): OverEager-Bench, 500 validated scenarios, about 7,500 runs across four agent products and six base models. The permissive cluster (Claude Code, Codex CLI, Gemini CLI) showed overeager rates of 5.4% to 27.7%; OpenHands, which asks before continuing, 0.2% to 4.5% (Fisher p ≤ 10⁻⁵). Within one framework the rate varied by up to 15.9 points across base models. — [arXiv 2605.18583](https://arxiv.org/abs/2605.18583)
- **[MEASURED] (abstract only)** Same paper: on Claude Code, removing the consent declaration from the prompt raised the overeager rate from 0.0% to 17.1% on paired scenarios (McNemar exact p = 2.4 × 10⁻⁴); across every shared base model the increase was 11.9 to 17.2 points. Explicit statements of what is in scope sharply reduce out-of-scope actions. — [arXiv 2605.18583](https://arxiv.org/abs/2605.18583)
- **[MEASURED] (primary read)** In PR data, specifications "do not constrain the scope of AI-tagged changes" (p = 0.997). — [ESEM 2026](https://drops.dagstuhl.de/storage/00lipics/lipics-vol394-esem2026/LIPIcs.ESEM.2026.84/LIPIcs.ESEM.2026.84.pdf)

### Inferences
- Two distinct mechanisms exist for turning a vague prompt into a workable target: (a) the agent expands it into a requirements document by assumption, or (b) the agent asks the user. All the positive measured evidence found is for (b). Evidence for (a) is absent, and the one anecdote (Kiro) shows inflation.
- An agent-written requirements document is itself a set of "unwarranted assumptions" in Ambig-SWE's terms unless a human confirms it. Writing them down makes them reviewable, but Böckeler's experience is that long generated specs are tedious and less likely to be reviewed carefully than code.
- Models "struggle to distinguish between well-specified and underspecified instructions", so a workflow cannot rely on the agent to decide when elaboration is needed; the 69.40% vs 61.20% result suggests a dedicated detection step is worth more than uniform elaboration.
- The consent-declaration result suggests that the cheapest scope control is a short explicit statement of what is and is not in scope, rather than a long specification.

### Gaps
- No study found that measures over-engineering (extra abstractions, unrequested features, diff size) as a function of whether the agent first wrote a requirements document.
- No measured data found on "goal drift" across a multi-step spec, plan, implement, review pipeline (i.e. the final diff answering the spec rather than the original user request).
- Ambig-SWE model names and per-model numbers were not extracted (abstract only).

## 5. What do practitioners and vendor guides recommend about how much upfront planning, and for which task sizes?

### Takeaway
Current guidance converges on proportionality: specs and plans for large, unclear or multi-session work; plain specific prompts for small, clear changes. The strongest universal recommendation is not planning but giving the agent an independent way to check its work.

### Cited Findings
- **[GUIDE] (primary read, page as of Nov 2026)** Anthropic's Claude Code best-practices page opens by saying that "in most cases, your first plain prompt in a fresh session already does the right thing, without any setup on your part"; setup is for when the project has knowledge, rules or constraints "that Claude can't see from the code alone". — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **[GUIDE] (primary read)** On specificity rather than planning: "If you name the file, describe the symptom, and say what "fixed" looks like up front, you usually save yourself a round of corrections later." A vague prompt is "completely fine" when exploring: "You'll correct a bit more as you go, and that's the trade-off." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **[GUIDE] (primary read)** A spec is recommended for the case where the USER has not decided what they want, and it is produced by interviewing the user, not by agent assumption: "Interview me until you could write the spec, then write it to SPEC.md." Claude "comes back with multiple-choice questions about the parts you haven't pinned down ... what's out of scope. It keeps asking until the answers add up to a spec." Then start a fresh session "so the build begins with a clean context and a written definition of done." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **[GUIDE] (primary read)** Verification is framed as the main lever: sessions go wrong when "Claude said it was done and it wasn't quite, usually because it had no way to check its own work." Before leaving a task unattended: "Does it know what done looks like? A goal condition, a spec file, or a failing test it has to turn green." Review is by a separate context: "You're reviewing code you didn't write. Compare the changed files against the spec you're given". — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **[GUIDE] (primary read, negative observation)** A text search of the fetched page for "plan mode" and "planning" returned no matches; the current version of this page does not present explore-plan-code as a default workflow. (Earlier versions of Anthropic's guidance did recommend it; I did not fetch an archived copy, so the change is my observation, not a documented statement.) — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **[ANECDOTE/OPINION] (primary read)** Thoughtworks' Böckeler: "very skeptical that lots of up-front spec design is a good idea"; favours small, iterative steps; none of the three tools reviewed fits "the majority of real life coding problems"; an effective tool would need to offer different workflows for different problem sizes. — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **[MEASURED, qualitative] (abstract only)** In interviews with 21 practitioners including eight tool makers, SDD was "used ... selectively and mainly for new features". — [arXiv 2608.25202](https://arxiv.org/abs/2608.25202)
- **[VENDOR-MEASURED] (primary read)** Task-size data consistent with this advice: no-spec matched the best spec workflows on small tickets (85%) and bug fixes (90%) and lost on large tickets (50% vs 80%). — [Uvik benchmark](https://uvik.net/blog/spec-driven-development-benchmark/)
- **(search snippet, secondary)** Thoughtworks reportedly listed spec-driven development in Technology Radar Vol. 32; the ring/status was described by a secondary source as "worth adopting" and I did not verify the actual ring against thoughtworks.com. — [secondary commentary](https://dev.to/sam_curatedmcp/spec-driven-development-renamed-an-old-problem-it-didnt-solve-it-tags-ai-productivity-347a)

### Inferences
- Vendor guidance, practitioner critique, practitioner interviews and the one head-to-head benchmark all point the same way: make ceremony proportional to task size and uncertainty, with a fast path for small or clear changes.
- The guidance distinguishes "definition of done" (short, checkable: a goal condition, a failing test) from "specification document" (long, narrative). The former is recommended universally; the latter only when requirements are undecided or the work is large.
- Where a spec is recommended, its inputs come from the user (interview) and its check comes from an independent context (a reviewer subagent or fresh session), not from the implementing agent's own elaboration and own tests.

### Gaps
- I did not fetch OpenAI Codex, Cursor, GitHub Spec Kit or AWS Kiro official guidance in this session, so their recommended task-size thresholds are not recorded here.
- No quantitative threshold (lines changed, files touched, estimated minutes) for "when to plan" was found in any measured source; the vendor benchmark's small/medium/large labels were not defined in the material I read.
- Anthropic's earlier explore-plan-code guidance and any explicit statement about when to skip plan mode were not re-verified against an archived page.
