# Maintain a verification skill

A feature map rots the moment the app changes. This is the upkeep loop for a skill generated by `/create-verification-skill` (or any
project-local verification skill with a feature map). The unit of rigour is the feature: cover every feature file from source and
exercise every feature live.

## Outcomes

Pick one, and say which:

- **clean**: every feature got source and live coverage; nothing worth shipping.
- **changed**: one change ships proven doc, harness or map corrections (one commit, or one `/b-do` ticket if the user prefers).
- **blocked**: coverage could not finish or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Edit only the verification skill's own directory (`.bint/skills/verify-<app>/`: SKILL.md, `features/`, its scripts), then `bint sync`.
Never edit product code here: behaviour the map describes that the app no longer has is either doc drift (fix the map) or a product
regression (report it, don't paper over it in docs).

## Pass

0. **Locate the target**: the custom skill whose body has launch/drive sections and a feature map (`.bint/skills/verify-*/`). Several →
   ask which; none → stop and point at `/create-verification-skill`.
1. **Index hygiene**: read the feature map README and its sibling files; fix missing, extra, duplicate or dead entries.
2. **Source wave**: for each feature file, explain from source how the user-facing feature works, flag likely doc drift with citations
   (`file:line`), and write one live-verification recipe. Use the code graph (`cg_explore`, `cg_callers`). In an interactive session you
   may give each feature to a read-only sub-agent; inside a `bint run` step do them sequentially yourself.
3. **Reconcile**: every feature has a summary. Merge recipes into as few app states as practical. Spot-check cited drift. Sweep recent
   churn (`git log`) for user-facing surfaces missing from the map; require a concrete source path before calling one missing.
4. **Live pass** (required even when source looks clean). Follow the skill's own launch model. Exercise every feature at least once,
   holding three invariants: (1) doctor before the first drive, on each fresh session, and after any failed drive; reset or relaunch
   when doctor can't see the failure; (2) evidence captured so far survives every cleanup, checked at its named location; (3) nothing a
   drive started outlives its usefulness. A doctor failure caused by skill drift is drift: fix it and retry once before calling the pass
   `blocked`. A feature is `verified-unreachable` only with the concrete prerequisite and the route attempted. Any harness fix gets
   re-driven live before it ships.
5. **Triage**: wrong/missing user-POV description → doc drift, fix it. Working behaviour the harness can't drive → harness gap, fix it
   (scripts executable, invocation in the body). Broken app behaviour → product gap: record it for the user (a `/b-debug` ticket is the
   natural next step), keep it out of this change.
6. **Ship or stop**: `bint skill lint verify-<app>`, re-read every changed file, then commit/ticket for `changed`; report outcome and
   coverage honestly for `clean`/`blocked`.

Keep run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in the OS temp directory; don't commit them.
